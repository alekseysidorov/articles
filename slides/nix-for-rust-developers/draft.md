# Nix для Rust-разработчика

Алексей Сидоров | Ведущий Rust-разработчик

## Проблема

На словах Rust-проект выглядит просто:

```bash
cargo build
```

Но в реальности вокруг проекта быстро вырастает зоопарк:

- `rust-toolchain.toml` для версии Rust
- `clippy`, `rustfmt`, `taplo`, `typos`
- системные зависимости: `openssl`, `protobuf`, `pkg-config`, `clang`
- `scripts/`
- `.github/workflows/`
- иногда `Dockerfile`
- README с инструкцией "что ещё надо поставить руками"

В итоге у проекта несколько источников правды:

```text
Cargo.toml        → Rust-зависимости
rust-toolchain    → версия Rust
CI yaml           → проверки
Dockerfile        → окружение
scripts           → локальные команды
README            → ручная инструкция
```

И всё это постепенно расходится.

Типичные симптомы:

- локально всё работает, а в CI падает
- на macOS одно поведение, на Linux другое
- новый разработчик тратит полдня на подготовку среды
- README устаревает
- CI проверяет не совсем то же самое, что разработчик запускает локально

## Два коротких примера

### Tokio

https://github.com/tokio-rs/tokio/tree/master/.github/workflows

У больших Rust-проектов быстро разрастается CI:

- много workflow
- много проверок
- матрицы платформ и версий
- заметный объём YAML

Типичный фрагмент:

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest, macos-latest]
    rust: [stable, beta, nightly]
```

Смысл примера простой: логика проекта начинает жить отдельно от проекта.

---

### gstreamer-rs

https://github.com/snapview/gstreamer-rs/tree/master/ci  
https://github.com/snapview/gstreamer-rs?tab=readme-ov-file#installation

Здесь кроме Rust-кода есть ещё и тяжёлые системные зависимости.

На macOS установка выглядит примерно так:

```bash
brew install meson ninja pkg-config gstreamer gst-plugins-base
```

На Linux — уже иначе:

```bash
apt-get install -y libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev meson ninja-build pkg-config
```

То есть один и тот же проект требует разной ручной подготовки среды в зависимости от платформы.

## Что такое Nix

Если совсем коротко, Nix — это способ декларативно описать среду проекта.

Не только зависимости из `Cargo.toml`, а всю рабочую среду:

- какой нужен Rust
- какие нужны системные библиотеки
- какие нужны инструменты
- какие проверки считаются официальными
- какие команды проект умеет запускать

То есть идея Nix не в том, чтобы заменить `cargo`, а в том, чтобы сделать **среду и проверки частью проекта**.

---

## Чуть-чуть про архитектуру

У Nix есть несколько важных идей.

Во-первых, зависимости описываются явно.

Во-вторых, артефакты лежат в `store`, обычно в путях вида:

```text
/nix/store/<hash>-openssl-3.0.13
/nix/store/<hash>-rustc-1.78.0
```

Это означает, что результат привязан к своим входам.

На практике это даёт три полезных свойства:

- меньше неявных зависимостей от системы
- проще получать одинаковую среду на разных машинах
- проще автоматизировать воспроизводимую сборку и проверки

---

## Что такое flakes

Для практики можно думать так: `flake` — это стандартный формат Nix-проекта.

Обычно есть два файла:

```text
flake.nix
flake.lock
```

Где:

- `flake.nix` — описание проекта
- `flake.lock` — зафиксированные входы

Главный смысл `flakes` в том, что они делают среду **воспроизводимой во времени**.

Если у проекта есть `flake.nix` и `flake.lock`, то сценарий:

```bash
git clone
nix develop
```

означает не "собери что-нибудь похожее", а "получи среду из зафиксированных входов".

По смыслу это похоже на `Cargo.lock`, только не для crates, а для dev/build-окружения проекта.

---

## Структура flake

Упрощённо:

```text
flake
 ├ flake.nix
 ├ flake.lock
 ├ inputs
 └ outputs
      ├ devShells
      ├ checks
      ├ packages
      └ apps
```

Где:

- `inputs` — откуда берутся зависимости
- `outputs` — что проект экспортирует наружу

На практике нас обычно интересуют три вещи:

- `devShells`
- `checks`
- `apps` / `packages`

---

## Основные части

### `devShell`

Это среда разработки.

```bash
nix develop
```

Обычно она даёт:

- правильный Rust
- `clippy`, `rustfmt`, `taplo`
- системные зависимости вроде `openssl`, `protobuf`, `pkg-config`

То есть вместо "поставь руками вот это всё" у проекта появляется нормальная точка входа.

---

### `checks`

Это официальный набор проверок проекта.

```bash
nix flake check
```

Идея в том, что один и тот же набор можно запускать:

- локально
- в CI

То есть CI перестаёт быть отдельным местом, где вручную повторно описана логика проекта.

---

### `apps` / `packages`

Это команды и артефакты проекта.

Например:

```bash
nix run .#test
nix run .#lint
```

То есть проект может экспортировать стандартные точки входа, а не рассчитывать на набор shell-скриптов и договорённостей.

---

## Минимальный образ мысли

Если совсем коротко, Nix в Rust-проекте обычно нужен для трёх вещей:

1. `nix develop` — зайти в готовую среду
2. `nix flake check` — прогнать официальный набор проверок
3. `nix run .#...` — запускать стандартные команды проекта

Этого уже достаточно, чтобы получить практическую пользу.

## Заключение

Главный тезис здесь не в том, что Nix — это ещё один пакетный менеджер.

Главный тезис в другом:

> Nix позволяет сделать воспроизводимость автоматизированной.

Не "у нас где-то в README написано, как это повторить", а:

- среда описана в проекте
- проверки описаны в проекте
- команды описаны в проекте
- CI исполняет то же самое описание

Именно в этом его главная практическая ценность для Rust-разработки.

Особенно там, где есть:

- системные зависимости
- несколько платформ
- сложный CI
- дорогой onboarding

# Дополнительные материалы

## Что такое Nix в более широком смысле

Словом `Nix` обычно называют сразу несколько вещей:

- язык выражений
- пакетный менеджер и build system
- `nixpkgs`
- экосистему вокруг воспроизводимых сборок

В этой статье нас интересует прежде всего Nix как способ описания dev/build-среды проекта.

---

## Чем Nix отличается от NixOS

Это не одно и то же.

- `Nix` — инструмент для описания пакетов, сред и сборок
- `NixOS` — Linux-дистрибутив, построенный вокруг Nix

Для Rust-разработчика это важный момент: использовать `nix develop`, `flakes` и `checks` можно и на macOS, и на обычном Linux, без перехода на NixOS.

---

## Чем Nix отличается от Docker

Это разные слои.

Docker чаще отвечает на вопрос:

> В каком контейнере это запускать?

Nix чаще отвечает на вопрос:

> Из каких входов это собирается и какая среда нужна для разработки и проверки?

Практически:

- Docker удобен для упаковки и запуска
- Nix удобен для dev-окружения, CI и воспроизводимой сборки

Они не исключают друг друга.

---

## Почему `flake.lock` так важен

Если в проекте есть:

```text
flake.nix
flake.lock
```

то зафиксированы не только команды, но и входы, из которых строится окружение.

По смыслу это похоже на `Cargo.lock`, но уровнем выше: не только crates, а вся dev/build-среда.

---

## Немного истории

Nix вырос из идеи чистых и воспроизводимых сборок: пакет не должен незаметно зависеть от того, что случайно установлено в системе.

Отсюда происходят его ключевые свойства:

- явные зависимости
- изоляция сборки
- воспроизводимость
- возможность держать несколько версий пакетов одновременно
- адресуемое хранилище артефактов в `/nix/store`

---

## Почему он хорошо ложится на CI

Если проверки вынесены в `checks`, то CI можно сильно упростить.

Вместо длинной ручной раскладки шагов по YAML остаётся что-то вроде:

```yaml
- uses: cachix/install-nix-action@v27
- run: nix flake check
```

То есть CI становится исполнителем того, что уже описано в проекте.

## `direnv`

Для ежедневной работы удобно добавить `.envrc`:

```bash
use flake
```

Тогда среда активируется автоматически при входе в директорию проекта.

## Nix как launcher инструментов

Nix можно использовать и просто как способ запускать инструменты без глобальной установки:

```bash
nix run nixpkgs#jq
nix run nixpkgs#ripgrep
nix run nixpkgs#nodejs
```

Это удобно и для локальной работы, и для автоматизации.

---

## Где он особенно полезен в Rust

Nix особенно хорошо окупается, когда в проекте есть:

- `openssl-sys`
- `bindgen` и `libclang`
- `protobuf`
- `rdkafka`
- `gstreamer`
- заметная разница между macOS и Linux
- сложный CI

То есть везде, где `cargo build` — это только верхушка айсберга.
