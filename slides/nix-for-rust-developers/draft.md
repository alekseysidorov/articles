# Nix для Rust-разработчика

Алексей Сидоров | Ведущий Rust-разработчик

## Проблема

На словах Rust-проект выглядит просто:

```bash
cargo build
```

Но это только верхний слой.

В реальности вокруг проекта быстро появляется ещё одно окружение.  
И вот оно уже живёт не в одном месте, а сразу в нескольких.

Обычно там есть:

- `rust-toolchain.toml` для версии Rust
- `clippy`, `rustfmt`, `taplo`, `typos`
- системные зависимости: `openssl`, `protobuf`, `pkg-config`, `clang`
- `scripts/`
- `.github/workflows/`
- иногда `Dockerfile`
- README с инструкцией, что ещё надо поставить руками

По сути проблема не в том, что зависимостей много.

Проблема в том, что у проекта появляется несколько источников правды:

```text
Cargo.toml        → Rust-зависимости
rust-toolchain    → версия Rust
CI yaml           → проверки
Dockerfile        → окружение
scripts           → локальные команды
README            → ручная инструкция
```

И дальше всё это постепенно расходится.

На практике симптомы обычно такие:

- локально всё работает, а в CI падает
- на macOS одно поведение, на Linux другое
- новый разработчик тратит полдня на подготовку среды
- README устаревает
- CI проверяет не совсем то же самое, что разработчик запускает локально

https://github.com/snapview/gstreamer-rs/tree/master/ci

И это важно потому, что `cargo build` сам по себе эту проблему не решает.

## Что такое Nix

Если упростить, Nix — это способ декларативно описать среду проекта.

Не только зависимости из `Cargo.toml`, а вообще весь рабочий контекст:

- какой нужен Rust
- какие нужны системные библиотеки
- какие нужны инструменты
- какие проверки считаются официальными
- какие команды проект умеет запускать

По сути идея не в том, чтобы заменить `cargo`.

Ключевая идея в другом:  
сделать **среду, команды и проверки частью проекта**.

---

## Чуть-чуть про архитектуру

У Nix есть несколько базовых идей.

Во-первых, зависимости описываются явно.

Во-вторых, артефакты лежат в `store`, обычно в путях вида:

```text
/nix/store/<hash>-openssl-3.0.13
/nix/store/<hash>-rustc-1.78.0
```

Это значит, что результат привязан к своим входам.

На практике отсюда следует несколько полезных свойств:

- меньше неявных зависимостей от системы
- проще получать одинаковую среду на разных машинах
- проще автоматизировать воспроизводимую сборку и проверки

По сути это не магия.

Это довольно прямолинейная идея:  
если входы зафиксированы явно, результат становится предсказуемее.

---

## Что такое flakes

Для практики можно думать так: `flake` — это стандартный формат Nix-проекта.

Обычно есть два файла:

```text
flake.nix
flake.lock
```

Где:

- `flake.nix` — описание проекта
- `flake.lock` — зафиксированные входы

Ключевая идея тут в том, что flakes делают среду **воспроизводимой во времени**.

Если у проекта есть `flake.nix` и `flake.lock`, то сценарий:

```bash
git clone
nix develop
```

означает не “собери что-нибудь похожее”.

Он означает:  
“подними среду из зафиксированных входов”.

По смыслу это похоже на `Cargo.lock`, только уровнем выше.  
Не для crates, а для dev/build-окружения проекта.

---

## Структура flake

Если упростить, flake выглядит примерно так:

```text
flake
 ├ flake.nix
 ├ flake.lock
 ├ inputs
 └ outputs
      ├ devShells
      ├ checks
      ├ packages
      └ apps
```

Где:

- `inputs` — откуда берутся зависимости
- `outputs` — что проект экспортирует наружу

На практике в Rust-проекте чаще всего важны три вещи:

- `devShells`
- `checks`
- `apps` / `packages`

---

## Основные части

### `devShell`

Это среда разработки.

```bash
nix develop
```

По сути это нормальная точка входа в проект.

Обычно она даёт:

- правильный Rust
- `clippy`, `rustfmt`, `taplo`
- системные зависимости вроде `openssl`, `protobuf`, `pkg-config`

То есть вместо “поставь руками вот это всё” у проекта появляется одна команда, которая поднимает рабочую среду.

---

### `checks`

Это официальный набор проверок проекта.

```bash
nix flake check
```

Тут важно не само название команды.

Важно, что один и тот же набор можно запускать:
- локально
- в CI

Получается что CI перестаёт быть отдельным местом, где вручную повторно описана логика проекта.

---

### `apps` / `packages`

Это команды и артефакты проекта.

Например:

```bash
nix run .#test
nix run .#lint
```

По сути проект начинает экспортировать стандартные точки входа.

То есть вместо набора shell-скриптов и договорённостей появляется явное описание того, что проект умеет запускать.

---

## Минимальный образ мысли

Если совсем коротко, Nix в Rust-проекте обычно нужен для трёх вещей:

1. `nix develop` — зайти в готовую среду
2. `nix flake check` — прогнать официальный набор проверок
3. `nix run .#...` — запускать стандартные команды проекта

На практике этого уже достаточно, чтобы получить ощутимую пользу.

Не нужно сначала понимать весь Nix.  
Достаточно начать с этих трёх точек входа.

## Заключение

Главный тезис тут не в том, что Nix — это ещё один пакетный менеджер.

Ключевая идея в другом:

> Nix позволяет сделать воспроизводимость автоматизированной.

Не “у нас где-то в README написано, как это повторить”.

А:
- среда описана в проекте
- проверки описаны в проекте
- команды описаны в проекте
- CI исполняет то же самое описание

По сути в этом и есть его практическая ценность для Rust-разработки.

Особенно там, где есть:
- системные зависимости
- несколько платформ
- сложный CI
- дорогой onboarding

# Дополнительные материалы

## Что такое Nix в более широком смысле

Словом `Nix` обычно называют сразу несколько вещей:

- язык выражений
- пакетный менеджер и build system
- `nixpkgs`
- экосистему вокруг воспроизводимых сборок

Но в этом докладе нас интересует прежде всего Nix как способ описания dev/build-среды проекта.

---

## Чем Nix отличается от NixOS

Это не одно и то же.

- `Nix` — инструмент для описания пакетов, сред и сборок
- `NixOS` — Linux-дистрибутив, построенный вокруг Nix

Это важный момент.

Для Rust-разработчика отсюда следует простая практическая вещь:  
использовать `nix develop`, `flakes` и `checks` можно и на macOS, и на обычном Linux, без перехода на NixOS.

---

## Чем Nix отличается от Docker

Это разные слои.

Docker чаще отвечает на вопрос:

> В каком контейнере это запускать?

Nix чаще отвечает на вопрос:

> Из каких входов это собирается и какая среда нужна для разработки и проверки?

На практике получается так:

- Docker удобен для упаковки и запуска
- Nix удобен для dev-окружения, CI и воспроизводимой сборки

Они не исключают друг друга.

---

## Почему `flake.lock` так важен

Если в проекте есть:

```text
flake.nix
flake.lock
```

значит зафиксированы не только команды, но и входы, из которых строится окружение.

По смыслу это похоже на `Cargo.lock`, но уровнем выше.

Не только crates, а вся dev/build-среда.

Это важно потому, что воспроизводимость без фиксации входов быстро становится условной.

## Немного истории

Nix вырос из идеи чистых и воспроизводимых сборок.

Если упростить, мысль была такая:  
пакет не должен незаметно зависеть от того, что случайно установлено в системе.

Отсюда следуют его базовые свойства:

- явные зависимости
- изоляция сборки
- воспроизводимость
- возможность держать несколько версий пакетов одновременно
- адресуемое хранилище артефактов в `/nix/store`

---

## Почему он хорошо ложится на CI

Если проверки вынесены в `checks`, CI можно сильно упростить.

Вместо длинной ручной раскладки шагов по YAML остаётся что-то вроде:

```yaml
- uses: cachix/install-nix-action@v27
- run: nix flake check
```

По сути CI становится исполнителем того, что уже описано в проекте.

И это важно потому, что источник истины остаётся один.

## `direnv`

Для ежедневной работы удобно добавить `.envrc`:

```bash
use flake
```

Тогда среда активируется автоматически при входе в директорию проекта.

На практике это убирает лишнее трение в повседневной работе.

---

## Nix как launcher инструментов

Nix можно использовать и просто как способ запускать инструменты без глобальной установки:

```bash
nix run nixpkgs#jq
nix run nixpkgs#ripgrep
nix run nixpkgs#nodejs
```

Это удобно и для локальной работы, и для автоматизации.

По сути Nix здесь выступает как воспроизводимый launcher для tooling.

---

## Где он особенно полезен в Rust

Nix особенно хорошо окупается, когда в проекте есть:

- `openssl-sys`
- `bindgen` и `libclang`
- `protobuf`
- `rdkafka`
- `gstreamer`
- заметная разница между macOS и Linux
- сложный CI

То есть везде, где `cargo build` — это только верхушка айсберга.

Если посмотреть на такие проекты, проблема обычно не в сборке Rust-кода как таковой.

Проблема в окружении вокруг него.  
И по сути именно эту проблему Nix и закрывает.
